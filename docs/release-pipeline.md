# Сборки и выпуски

Workflow: `.github/workflows/android.yml` — **Android CI and preview releases**.

## Когда запускается

| Событие | Проверки | Результат |
|---|---|---|
| Push в main, PR в main | JDK 17, Android SDK 34/build-tools 34.0.0, JVM-тесты, debug APK, lint, тесты метаданных | APK с описанием и SHA-256, отчёты на 14 дней |
| Run workflow | Те же проверки с постоянной preview-подписью; по умолчанию две регрессии на Android 15 | Подписанный тестовый пакет и отчёты, без нового Release |
| Push тега vX.Y.Z | Проверки версии, подписи, сборка и обе регрессии на Android 15 | Черновик pre-release с подписанным APK и пометками совместимости |

Сборка на PR не получает ключ подписи. Её APK подписан временным CI-ключом и помечен как `ci-debug`: для отдельной тестовой установки, не для обновления установленных preview-релизов. Теги и ручные запуски используют `preview-debug` с той же подписью, что и v0.2.1.

## Подпись

В GitHub Actions Secrets хранится `ANDROID_DEBUG_KEYSTORE_BASE64` — текущий тестовый keystore. GitHub CLI шифрует значение перед отправкой. Keystore и токен не хранятся в Git или файлах workflow. Временный файл ключа удаляется после упаковки; задания эмулятора и публикации ключ не получают.

Публичный SHA-256 сертификата: `b3e3703d07d76a6474ef19620632a092763d101db5750ab2c00f311582e8358f`. Упаковка preview прекращается, если подпись отличается. Локальная копия текущего тестового ключа остаётся в существующем Android keystore; её нужно сохранить вне репозитория для будущих обновлений.

Это тестовая debug-подпись, не production-релиз для Google Play. Переход на постоянный production-ключ должен быть отдельным решением о миграции приложения и данных; pipeline не меняет подпись установленных preview-версий.

## Следующий выпуск

1. Обновить `versionName` и увеличить `versionCode` в `app/build.gradle.kts`. Сейчас основная версия — `0.2.1`, code 3; следующий пример — `0.2.2`, code 4. Суффикс `-reader-design` допускается, основная версия должна совпадать с тегом.
2. Закоммитить, отправить main и дождаться зелёной проверки.
3. Создать аннотированный тег на проверенном коммите, например `git tag -a v0.2.2 -m "Flibusta Reader 0.2.2"`, затем `git push origin v0.2.2`.
4. Дождаться сборки, двух регрессий на эмуляторе и подготовки черновика в GitHub Releases.
5. Скачать preview APK из черновика или Actions artifacts, проверить на физическом телефоне, затем опубликовать Release. Пока приложение — прототип, оставить пометку Pre-release.

Теги не перемещать. Опубликованные релизы pipeline не перезаписывает. При временном сбое загрузки можно повторить release job: незавершённый черновик с тем же содержимым и совпадающими SHA-256 дополняется недостающими файлами. Несовпадающие файлы или чужой черновик вызывают ошибку.

## Вложения и совместимость

- `FlibustaReader-vX.Y.Z-android14plus-universal-preview-debug.apk`: телефоны и планшеты Android 14+, универсальная тестовая сборка с постоянной preview-подписью.
- `README-release-ru.md`: для кого APK, инструкция обновления, ограничения, версия/коммит, результаты этапов pipeline.
- `SHA256SUMS.txt`: контрольные суммы APK, описания и метаданных.
- `release-metadata.json`: версия, minSdk, имя APK и сертификат.

Эмуляторный job проверяет пакет по SHA-256 до установки. `reader-background-regression.ps1` проверяет завершение подготовки в фоне; `reader-regression.ps1` — восстановление файлов/данных чтения и поиска после смерти процесса, поворот, геометрию и типографику. Живой каталог и физический телефон не входят в автоматическую проверку.

## Локальная проверка

`./scripts/build.ps1` продолжает работать как прежде. Тесты упаковки: `./scripts/test-release-metadata.ps1`. Упаковка CI-пакета: `./scripts/package-release.ps1`. Для preview передать `-SigningKind preview -ExpectedCertificateSha256 <указанный выше SHA-256>`. В оба Android regression-скрипта можно передать `-Apk`, `-Adb` и `-Serial`.
